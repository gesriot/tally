# tally-store

Хранилище Tally на SQLite (`rusqlite` со встроенной SQLite): схема, миграции,
CRUD для всех записей `tally-core`, мягкое удаление и поиск по кириллице.

```sh
cargo run -p tally-store --example store   # база в файле: запись, списки, поиск, корзина
cargo test -p tally-store
```

## API

- `Store::open(path)` / `Store::open_in_memory()` – соединение (`foreign_keys = ON`,
  WAL для файла) и миграции до `SCHEMA_VERSION`.
- `store.read()` → `Reader`: `task(id)`, `tasks()`, то же для проектов, областей,
  разделов и тегов; `snapshot()` – вся база для `tally_core::lists`; `search(query)`.
  `snapshot()`, `area(s)`, `project(s)`, `task(s)` и `search()` читают запись
  вместе с тегами и чек-листом в одной транзакции: в WAL это один
  согласованный снимок, даже если рядом пишет другое соединение.
- `store.write(|w| …)` → `Writer` внутри одной транзакции (`BEGIN IMMEDIATE`):
  `insert_*`, `update_*`, `delete(RecordId, at)` и `restore` (корзина),
  `purge(RecordId)`, `empty_trash()`. Ошибка в замыкании откатывает всё.
  Каждая операция `Writer` атомарна сама по себе (SAVEPOINT): если замыкание
  поймало ошибку операции и вернуло `Ok`, фиксируются только целые операции.
  Писать вне транзакции нельзя – у `Writer` нет публичного конструктора.
- Журнал действий для отмены и повтора (`tally-app`): `Writer::push_history(at,
  action, changes, keep)` – новое действие (отменённые стираются, остаются последние
  `keep`), `Writer::mark_history(seq, undone, changes)` – отметить отменённым или
  повторённым; `Reader::last_done()` – что отменит undo, `first_undone()` – что
  повторит redo, `history()` – весь журнал (`HistoryEntry`). `changes` – текст
  вызывающего кода, хранилище его не разбирает. Пишется в той же транзакции, что
  и само действие, и откатывается вместе с ним.
- `purge(RecordId)` стирает только то, что в «Корзине»: удалённое само или лежащее
  в удалённом проекте, разделе или области. Иначе – `NotInTrash`.
- `empty_trash()` стирает всё удалённое с содержимым и надгробия пунктов
  чек-листа, в том числе у живых задач; `Purged` – сколько чего ушло.

Ошибки – `StoreError`: `NotFound`, `AlreadyExists`, `MissingReference`,
`HeadingOutsideProject` (раздел задачи из другого проекта или задача без проекта),
`AreaWithProject` (своя область у задачи в проекте), `DuplicateChecklistItem`,
`StaleTimestamp` (метка переноса раздела старше изменений его или его задач),
`NotInTrash`, `DuplicateTag`, `Corrupt` (значение в базе не разбирается),
`NewerSchema`, `Sqlite`.

## Схема

Миграции `0001_init.sql`, `0002_history.sql`, `0003_repeat_anchor.sql` и `0004_remove_undated_repeats.sql`. Таблицы используют `STRICT`. Номер версии – `PRAGMA user_version`;
миграции только дописываются в конец и применяются каждая в своей транзакции
`BEGIN IMMEDIATE`; версия перечитывается уже под блокировкой записи, поэтому два
процесса, открывшие новую базу одновременно, не применят миграцию дважды.
Переход в WAL при занятом файле повторяется до `busy_timeout` (5 с).

- id – UUID текстом; у каждой записи `created_at`, `updated_at`, `deleted_at`.
- Даты – `YYYY-MM-DD`; моменты – UTC фиксированной ширины
  `2026-11-19T09:00:00.000000000Z`, поэтому сравнение строк = сравнение времени
  (пригодится синхронизации: индексы по `updated_at`).
- Порядок – строки `tally-rank` в `sort_index` и `today_index`; BINARY-сравнение
  SQLite совпадает с порядком `Rank`.
- Состояние – `status` + `closed_at`, повтор – `repeat_interval`, `repeat_unit`,
  `repeat_from`; несовместимые сочетания отсекают `CHECK`.
- Теги – таблицы `task_tags`, `project_tags`, `area_tags` с `position` (порядок
  тегов у записи). Чек-лист – `checklist_items`, сохраняется вместе с задачей:
  пункт, убранный из `Task.checklist`, получает `deleted_at` и остаётся надгробием
  (для синхронизации) до очистки корзины; поиск его не видит.
- Раздел задачи – раздел её проекта: составная ссылка
  `(heading_id, project_id) → headings (id, project_id)` и `CHECK` «нет раздела
  без проекта»; `Writer` проверяет то же заранее и отвечает `HeadingOutsideProject`.
  Перенос раздела в другой проект переносит и его задачи (`ON UPDATE CASCADE`),
  а их `updated_at` становится временем правки раздела – выборка изменений по
  времени их увидит. Метка переноса не может быть раньше последнего изменения самого
  раздела или любой его задачи (`created_at`/`updated_at`): такой перенос
  отклоняется с `StaleTimestamp` и ничего не меняет – вызывающий код повторяет
  его с текущим временем. Повтор начинается с перечитывания раздела внутри новой
  `write`-транзакции: перенос применяется к свежей записи, и только ей ставится новое
  время. `update_heading` сохраняет запись целиком, поэтому старая копия `Heading`
  с одной лишь обновлённой меткой вернула бы, например, прежнее название.
- Своей области у задачи в проекте нет: `CHECK (project_id IS NULL OR area_id IS NULL)`,
  `Writer` отвечает `AreaWithProject`. Область такой задачи – область проекта,
  поэтому перенос проекта в другую область строки задач не меняет и их
  `updated_at` не трогает: изменилась только запись проекта.
- Пункты чек-листа одной задачи с одинаковым id отклоняются
  (`DuplicateChecklistItem`), операция откатывается целиком.
- Ссылки: при физическом удалении (очистка корзины, `purge`) проект уносит свои
  разделы и задачи, раздел – свои задачи, область – свои проекты (а с ними их
  задачи) и задачи прямо в ней (`ON DELETE CASCADE`), как в Things. Ссылка на
  родительский тег обнуляется (`SET NULL`). Мягкое удаление ничего не каскадирует:
  ставится только `deleted_at` самой записи, содержимое «наследует» корзину по
  правилам `tally-core` и возвращается при восстановлении.

## Поиск

`LIKE` и `lower()` в SQLite понимают регистр только у ASCII, поэтому колонку
`search_text` заполняет Rust (`normalize`): разложение NFD, Unicode-нижний регистр,
снова NFD, «ё» → «е» на разложенном тексте (убирается U+0308 после «е»), сборка
NFC. Так функция идемпотентна и для «J» + U+030C, и для «Ё» + U+0300 (property-тест
по кириллице с комбинируемыми знаками),
пробелы схлопнуты. У задачи туда входят название, заметки и пункты чек-листа,
у проекта – название и заметки, у области и тега – название.

Запрос нормализуется так же и делится на слова; каждое слово должно быть
подстрокой (`instr`, без спецсимволов `LIKE`). Удалённое не находится, в том числе
задачи удалённого проекта, раздела или области и проекты удалённой области: SQL
отдаёт признаки цепочки удаления, а решает `tally_core::lists::Deleted` – то же
правило, что у списков.
Порядок: совпадение в названии, открытые раньше выполненных, затем области,
проекты, теги, задачи. При росте объёма поверх той же колонки встанет FTS5.
