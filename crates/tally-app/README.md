# tally-app

Слой приложения Tally: команды над `tally-store`, отмена и повтор, поток – владелец базы. Консоль (`tally-cli`) и окно (`tally-ui`) только переводят ввод в команды и показывают результат; правила – здесь и ниже.

```sh
cargo test -p tally-app
```

## API

- `Command` – изменение базы: `AddTask(NewTask)`, `Close(Close)` (выполнить или отменить задачи), `MoveTask(MoveTask)`, `AddProject`, `AddArea`, `AddHeading`, `Undo`, `Redo`, `UndoStep(seq)` (отменить действие с этим номером журнала, только если оно последнее, см. «Отмена конкретного действия»). Значения – как их ввёл пользователь: названия, начала номеров задач, выражения дат («завтра вечером», «15 дек»); разбирает их `tally-app` (`tally-when`).
- `execute(&mut Store, &Command, Clock) -> Result<Done>` – выполнить команду. `Clock { today, now }` – сегодняшний день и время команды: `now()` слой не вызывает. `Done { effect, snapshot, seq }` – что сделано (`Effect::Added(TaskId)`, `Closed`, `Moved`, `ProjectAdded`, …, `Undone(Step)`, `Redone(Step)`), база сразу после команды, прочитанная в той же транзакции, и `seq` – номер строки журнала, которую команда записала (у undo и redo – которую отменили или повторили); `None` – команда ничего не изменила.
- `snapshot(&Store)`, `search(&Store, запрос)` – чтение: один согласованный снимок; совпадения поиска и снимок для их вывода – из одного состояния базы.
- `Service` – один интерфейс (`execute`, `snapshot`, `search`) для синхронного `App` и потока `Worker`. `Worker::spawn(store)` отдаёт хранилище своему потоку; запросы идут через канал и выполняются по одному, по порядку. Поток заканчивается вместе с `Worker`.
- `Index` – поиск в снимке: проект, раздел и область задачи, её список по правилам `tally-core`, короткие номера (`[3f9a2c] Купить хлеб`), задача по началу номера или части названия (`resolve`). `id_len`, `short`, `hex`, `candidate_id_len` – правила коротких номеров.
- `Error`: `Rejected` (нет задачи, неверная дата, одноимённые записи, задача уже закрыта, неверные значения команды), `NothingToUndo` («нечего отменять»), `NothingToRedo` («нечего повторять»), `NotLast` («после этого действия было другое действие», только `UndoStep`), `Conflict`, `NoLaterTime` (время правки записи уже `Timestamp::MAX`), `History` (строка журнала не читается), `Stopped` (поток `Worker` остановлен), `Store`. Если команда вернула ошибку, в базе ничего не изменилось.

## Проверки команд

Окно будет вызывать тот же API напрямую, поэтому всё, что консоль отсекает разбором аргументов, `tally-app` проверяет сам и отвечает `Rejected`, ничего не записывая:

- пустые (или из пробелов) название задачи, проекта, области, раздела, тега, значение «когда» и срок: «пустое название тега», «пустое значение «когда»», «пустой срок»;
- `AddTask`: раздел без проекта – «раздел указывается вместе с проектом»; проект и область сразу – «задача не может быть сразу в проекте и в области»;
- `Close` без задач – «не указаны задачи»;
- `MoveTask`: несовместимые изменения – «несовместимые изменения: во «Входящие» и дата» (так же проект и область, раздел и без проекта, срок и без срока и другие сочетания, которые запрещает `tally move`).
- новая или изменённая ссылка любой команды (проект, раздел, область, теги; раздел и область у создаваемых проекта и раздела) ведёт только на живое – той же проверкой цепочки, что у отмены и повтора (одна функция на оба случая): «раздел «Ванная»: проект «Ремонт» закрыт» для `move --heading Ванная` у задачи закрытого проекта. Указать прежний раздел и вынести задачу из закрытого проекта или архивного раздела можно. Поэтому любую успешную команду можно сразу отменить и повторить; `tests/fixes3.rs` проверяет это перебором команд и состояний контейнеров.

## Команда без изменений

Если после команды каждая затронутая запись совпадает с прежней по всему, кроме времени правки (например, `move --no-deadline` у задачи без срока), транзакция откатывается: метки остаются прежними, строки журнала нет, ветка повтора не стирается. Команда при этом успешна и возвращает обычный результат.

## Порядок выполнения команды

Команда сама ничего не пишет: по снимку базы она только говорит, какими станут записи. Дальше `tally-app` в той же транзакции и строго по порядку:

1. отбрасывает записи, которые не изменились (кроме времени правки); не осталось ни одной – успех без изменений, ничего не пишется;
2. проверяет новые и изменённые ссылки на базе, какой она станет, – до любой записи (`Rejected`);
3. ставит изменяемым записям время правки – здесь и только здесь возможен `NoLaterTime`, то есть лишь для настоящей и допустимой правки: на `Timestamp::MAX` недопустимая ссылка – `Rejected` с причиной, перенос без изменений – успех;
4. пишет записи и строку журнала.

Отмена и повтор устроены так же: сверка, ссылки на удаляемое и связи, затем метки всех записей шага и только потом запись. Любой отказ откатывает транзакцию целиком.

## Прежний контейнер по названию

`MoveTask` ищет проект и раздел по названию среди живых (открытый проект не в корзине, раздел не в корзине и не в архиве). Если живого с таким названием нет, но так называется текущий проект или раздел задачи (закрытый проект, архивный раздел), ссылка остаётся прежней: `move <UUID> --heading Кухня` у задачи в архивной «Кухне» – успех без изменений. Живой одноимённый раздел выигрывает, только если в него можно перенести задачу: проверка его цепочки та же, что у ссылок команд (раздел, его проект не закрыт и не в корзине, область проекта не в корзине). В открытом «Ремонте» `--heading Кухня` у задачи в архивной «Кухне» переносит её в живую «Кухню»; в закрытом «Ремонте» доступной другой «Кухни» нет – ссылка остаётся прежней, успех без изменений, а `--heading Ванная` – отказ «раздел «Ванная»: проект «Ремонт» закрыт». Недоступные одноимённые разделы отбрасываются до проверки на неоднозначность: несколько доступных – отказ со списком только их (в открытом «Ремонте» две живые «Кухни» – «в проекте «Ремонт» разделов «Кухня» несколько:»), один – он, ни одного – прежний раздел задачи с этим названием (в закрытом «Ремонте» с двумя живыми «Кухнями» задача из архивной «Кухни» остаётся на месте, код 0), нет и его – отказ с настоящей причиной («раздел «Кухня»: проект «Ремонт» закрыт» у задачи из «Ванной»). Проект, область и тег по названию ищутся только среди доступных (проект открыт и не в корзине вместе с областью, область и тег не в корзине) – там отбор и так идёт до проверки на неоднозначность, поэтому для `-p`, `-a` и `-t` правило то же само собой. Задачи в корзине (сами или через раздел, проект, область) команды не находят: `move` не восстанавливает из корзины.

## Команда – одна транзакция

Снимок, поиск записей, все проверки, запись и строка журнала действий – в одной транзакции записи (`BEGIN IMMEDIATE`). Другой клиент не вклинится между чтением и записью, любая ошибка откатывает всё, включая журнал.

Время создания и закрытия записей – время команды. Время правки изменяемой записи – время команды, но не раньше прежних меток самой записи: если её правили «из будущего», новая правка на наносекунду позже. Метки других записей на это не влияют. Метка растёт строго: если прежняя метка – `Timestamp::MAX`, расти некуда, и правка (команда, отмена или повтор) отвечает `NoLaterTime`, ничего не записывая. Метка вычисляется только после того, как ясно, что запись действительно меняется: перенос без изменений на пределе меток успешен, как и любой другой.

## Журнал действий

Таблица `history` (миграция `tally-store/migrations/0002_history.sql`):

| Колонка | Что хранит |
|---|---|
| `seq` | Номер, `AUTOINCREMENT`: чем больше, тем новее |
| `at` | Время действия |
| `action` | Название для вывода: «перенос задачи «Отчёт»» |
| `changes` | JSON: для каждой записи, которую действие изменило, – `before` и `after` (запись целиком, `null` – записи нет) и `stamp` – последняя метка правки, которую журнал ей поставил ; `chain_before` и `chain_after` – цепочка контейнеров записи (см. «Связи восстанавливаемого») |
| `undone` | 1 – действие отменено и ждёт повтора |

Все отменённые строки новее всех неотменённых. `undo` берёт самое новое неотменённое действие, `redo` – самое старое отменённое. Новое действие стирает отменённые. Помнятся последние `HISTORY_LIMIT` = 100 действий. Журнал один на базу: его видят все клиенты, и он переживает перезапуск.

Обратная команда не вычисляется заново, а берётся из сохранённых состояний: отмена возвращает каждую запись в `before`, повтор – в `after`. Поэтому возвращаются все поля, которые команда тронула. Состояния «после» читаются из базы в той же транзакции, что и запись, – это ровно то, что сохранено.

- **Порядок.** Отмена идёт с конца действия (задача раньше тегов, которые она создала), повтор – по порядку.
- **Удаление.** Запись, которой до действия не было, отмена удаляет физически (а не в «Корзину»), повтор вставляет снова с тем же id и временем создания.
- **Даты не разбираются заново.** «Завтра» в повторе – день, который был завтра в момент команды; время выполнения при повторе `done` – прежнее.
- **Время правки.** Каждая запись при отмене и повторе получает метку `max(время команды, последняя метка записи + 1 нс)`. Последняя метка – наибольшая из текущей метки записи и `stamp` журнала: запись, которую отмена удалила, повтор вернёт позже метки удаления, даже если часы ушли назад. После шага новое состояние записи (с новой меткой) сохраняется в `changes`.
- **Сверка.** Перед записью каждая запись сравнивается с тем, что оставило действие (или его отмена), по всем полям, кроме времени правки самой записи и её пунктов чек-листа: эти метки двигают вперёд сами отмена и повтор или другой клиент, не меняя содержимого. Текст, отметка и удаление пункта сравниваются. Не совпала – `Conflict`, ничего не пишется, строка журнала остаётся на месте: «нельзя отменить перенос задачи «Отчёт»: задачу [3f9a2c] Отчёт за ноябрь изменили после этого действия», «… удалили после этого действия».
- **Метки пунктов чек-листа** тоже только растут: пункт, у которого другой клиент обновил только метку, сохраняет более свежую; пункт, который шаг меняет, получает метку позже обеих.
- **Ссылки на удаляемое.** Запись, которую шаг удалил бы, не должна быть нужна записям вне действия (задача в проекте, раздел проекта, проект области, тег у задачи, проекта или области, вложенный тег): иначе `Conflict` «на проект «Ремонт» ссылается задача [3f9a2c] Плитка». Поэтому тег, созданный добавлением, уходит при отмене, только если на него больше никто не ссылается; тег, который был до действия, отмена не трогает.
- **Связи восстанавливаемого.** База после шага проверяется целиком (записи шага уже в целевом состоянии). Связь, которую шаг ставит заново или меняет, должна вести на живую запись со всей её цепочкой: запись есть в базе, не в корзине и не в архиве; для раздела – его проект есть, не в корзине, не закрыт, и область проекта не в корзине; для проекта – он не закрыт и его область не в корзине. Раздел задачи всегда должен быть разделом её проекта. Иначе `Conflict` с названием: «проект «Дача» в корзине», «проект «Дача» закрыт», «область «Дом» проекта «Ремонт» в корзине», «раздел «Кухня» в корзине», «раздел «Кухня» в архиве», «раздел «Кухня»: проект «Ремонт» в корзине», «раздел «Кухня» теперь в проекте «Дача»», «область «Дом» в корзине», «тег «Срочно» в корзине», «проекта [3f9a2c1b] нет в базе».
  Пример с архивным разделом: «Плитку» перенесли из «Кухни» в «Ванную», потом «Кухню» убрали в архив. `undo` вернул бы «Плитку» в «Кухню», то есть восстановил бы ссылку на архивный раздел, поэтому отвечает «нельзя отменить перенос задачи «Плитка»: раздел «Кухня» в архиве». Конфликт возникает только тогда, когда ссылку на раздел восстанавливают или ставят заново. Контейнер, который действие застало таким же (закрытым, в архиве, в корзине) и который с тех пор не изменился, тоже не мешает: задачу вынесли из закрытого «Ремонта» – отмена вернёт её туда; а если «Ремонт» закрыли уже после действия – конфликт «проект «Ремонт» закрыт». Для этого журнал хранит у каждого изменения цепочку контейнеров записи до и после действия (поля `chain_before` и `chain_after`): только id, связь с родителем (область проекта, проект раздела, родитель тега) и доступность – в корзине ли, закрыт ли проект, в архиве ли раздел. Названия и заметки туда не попадают и не сравниваются: переименовать закрытый проект или поменять его заметку – отмене не мешает; убрать в корзину – мешает, пока не вернули. Для ссылки на проект «выполнен» и «отменён» равнозначны – оба закрывают проект (сам статус проекта, конечно, различается). Строки журнала старого формата хранили цепочку полными записями (`around_before`, `around_after`): при чтении они переводятся в те же флаги, а при первой отмене или повторе строка переписывается в новом виде – без названий и заметок. Поэтому вынос задачи из уже закрытого проекта, сделанный до обновления, после обновления по-прежнему отменяется, а закрытие проекта после выноса по-прежнему даёт конфликт. В строках без цепочки вовсе (самые старые строки) проверяется всё. Миграция базы не нужна. Связь, которую шаг не меняет, сохраняется и на корзину, архив и закрытие не проверяется: если «Плитку» выполнили в «Ванной», а «Ванную» потом убрали в архив (или «Ремонт» в корзину), отмена `done` всё равно откроет задачу в «Ванной». После конфликта ничего не записано, действие остаётся в журнале: когда причину убрали (раздел вернули из архива, проект или область – из корзины, раздел – в проект), отмена или повтор проходят.

Через `tally-app` журнал не расходится с базой: каждое изменение – действие в журнале, и отменяется сначала самое новое. Сверка ловит записи в обход журнала: другую программу, прямую запись через `tally-store`, будущую синхронизацию.

## Отмена конкретного действия

`UndoStep(seq)` – для окна: снять отметку с задачи – значит отменить именно её закрытие, а не то, что окажется последним в общем с консолью журнале. Окно запоминает `Done::seq` своего закрытия и отправляет его. В одной транзакции записи `tally-app` берёт последнее неотменённое действие и сверяет номер: совпал – дальше обычная отмена со всеми проверками (`Conflict` и т. д.); не совпал (после закрытия было другое действие, например `tally add` из консоли, или закрытие уже отменили) – `Error::NotLast`, база и журнал не меняются. Номера не переиспользуются (`AUTOINCREMENT`): затёртое отменённое действие не совпадёт с новым. Обычный `Undo` (Ctrl+Z, `tally undo`) работает с общей историей, как прежде.

## Тесты

```sh
cargo test -p tally-app
```

- `tests/undo.rs` – отмена и повтор: приёмочный сценарий (задача из раздела проекта переносится в другой проект на новую дату, отмена возвращает проект, раздел и дату, повтор – выбранный проект и новую дату), отмена `add` с новыми тегами, `done` и `done -c`, создания области, проекта и раздела, пустой журнал, стирание отменённого новой командой, предел журнала, конфликты (запись изменена, удалена, на неё ссылаются), метки «из будущего» и часы, ушедшие назад, журнал после перезапуска и из другого соединения, два одновременных `undo`, `Worker`.
- `tests/undo_step.rs` – `Done::seq` и `UndoStep`: вершина журнала сменилась, действие уже отменено или затёрто, обычные конфликты.
- `tests/links/` – ссылки команд, отмены и повтора ведут только на живые записи: корзина, закрытые проекты, архивные разделы, предельные метки времени, журнал в старом формате. Самый широкий – `links/command_outcomes.rs`: таблица ожидаемых исходов (изменение, без изменений или точный текст отказа) для 34 команд в 18 состояниях контейнеров; после каждого изменения `undo → redo → undo → redo` сверяется со снимками до и после команды целиком.
- `tests/repeats/` – календарные повторы и повторы после выполнения, повтор проекта, корзина и очистка, обновление базы со старой схемой.
- `tests/data/` – JSON-экспорт и импорт одним шагом истории, откат конфликтного импорта, суточные копии базы.
- `tests/drop_task.rs`, `tests/edit_task.rs`, `tests/organizations.rs` – перетаскивание, карточка задачи, проекты и области.
- Модульные тесты в `src/` – сравнение записей без времени правки (и с чек-листом), правило меток и их предел, метки пунктов, JSON журнала.
